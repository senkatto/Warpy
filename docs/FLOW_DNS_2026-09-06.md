# Flow hostname preservation on Windows

## Problem and change

The server's Flow domain rules did not cover connections whose destination
arrived only as an IP and could not be identified by protocol sniffing. Actual
Chrome-session logs included direct IPv4 TCP and UDP connections to addresses
also used by Flow and its API, alongside correctly routed IPv6 connections.
An initial server correction adding `flow.google.com` was necessary but did not
resolve the user's signed-in unsupported-country screen.

Windows now uses synthetic DNS answers only for `flow.google.com`, `labs.google`
and `aisandbox-pa.googleapis.com`. The VPN core restores the hostname before
forwarding, so routing does not depend on TLS/QUIC inspection or a shared Google
IP. HTTPS DNS records for these hosts return an empty successful answer. Other
domains and explicit bypass DNS rules retain their existing behavior.

No Google account settings, credentials, public versions or Android code changed.

## Verification

- All 106 JavaScript tests passed, including a new integration test using the
  bundled core. It obtains a synthetic DNS address, connects to that address
  without sending a ClientHello, and verifies the SOCKS upstream receives
  `flow.google.com`. LAN bypass is enabled during the test.
- Production Windows installer built, copied to
  `D:\Sync\VetomenAPK\Warpy-setup.exe`, and installed successfully.
- Restarted Warpy with the user's existing enabled automatic-connect preference.
  The service and tunnel resumed; Windows resolved Flow to `198.18.0.2` and its
  API to `198.18.0.3`.
- Requests from the installed Windows tunnel returned HTTP 200 for Flow and
  expected unauthenticated root HTTP 404 for the API. VPS access logs showed
  explicit hostnames and `google-ai-ipv6` for both, using the user's actual
  `warpy-vision` VLESS client.
- The open Chrome session still showed unsupported-country immediately after
  installation. A full browser restart after the DNS change was requested;
  signed-in Flow success is not yet verified.

## Diagnostic cleanup

A temporary server OUTPUT chain rejected UDP/443 only to nine resolved Flow/API
IPv4 addresses. It did not resolve the browser error and was removed completely
(OUTPUT jump, rules, and chain). No such firewall workaround remains active.

Chrome's internal socket-management page was blocked by the browser tool's
security policy; no workaround to access that page or force its operation was
used. The user was asked to restart the browser normally.
